01 — SHAPE

Two pipelines, one meeting point

The most common misreading of RAG is treating it as a single flow. It is two. Ingest is slow, batched, and runs when documents change. Query is fast, per-question, and never touches the raw files. They share only the store.

Track A · build time

Ingest — you run this when documents change

.\rag.cmd ingest --all

01Load Read every *.jsonl in data/tickets/
02Chunk Split by one of 3 strategies. Metadata rides along.
03Embed Bi-encoder, document side. Unit-normalized.
04Persist Vectors + chunks + meta.json provenance

↓   both tracks meet at the store   ↓

Track B · ask time

Query — runs per question, never reads the .jsonl files

.\rag.cmd ask "How long do refunds take?"

01Embed query Same model, query side — prefixes differ
02Filter + top-K Metadata narrows, then cosine picks 10
03Rerank Cross-encoder rescores, keeps top 3
04Score gate Below 0.20 → refuse, LLM never called
05Generate Answer from excerpts only, with citations
02 — TRACK A

Ingest, stage by stage

Nothing watches the folder. Re-run this after adding documents, changing a chunk preset, or switching the embedding model.

01

Load tickets tickets.py → load_all()

Globs data/tickets/*.jsonl, one JSON object per line, and concatenates every file it finds. Six fields are required: ticket_id, subject, product, category, status, priority. A malformed line names its own file and line number rather than failing silently.

ticket_id becomes the citation label — it is what appears as [TIC-1001] in the final answer.

02

Chunk chunking.py → build_chunks()

Three strategies. flat slices the whole corpus into character windows. ticket makes one chunk per ticket. section packs conversation turns under a repeated header so each fragment names its own ticket.

This is the decision that matters most. Not chunk size — strategy. See section 05.
03

Embed documents embed.py → encode_documents()

Turns each chunk into a 384-dimension vector positioned by meaning, so “why am I getting 429” lands near “rate limit exceeded” despite sharing no words.

Document and query encoding are deliberately separate methods. E5 needs passage: here and query: on the other track; BGE needs an instruction on queries only; MiniLM needs neither. Using the wrong one degrades retrieval with no error at all.

04

Persist store.py / qdrant_store.py

Writes vectors, chunks with their metadata, and a meta.json recording which embedding model built the index. Two backends behind one interface: numpy (exact brute force, fully inspectable) or Qdrant (real vector DB, embedded or server).

That provenance file is load-bearing. Swap the embedding model without re-ingesting and you would otherwise get either a raw shape error or — when dimensions happen to match, which is common — silently garbage rankings.

03 — TRACK B

Query, stage by stage

A funnel that gets narrower and more expensive at every step: thousands of chunks → 10 candidates → 3 finalists → one answer, or none.

01

Embed the question embed.py → encode_queries()

Same model as ingest, opposite side of the asymmetry.

02

Metadata filter, then top-K filters.py → retrieve.py

Optional --filter product=Billing narrows the candidate set before ranking. Then cosine similarity picks the nearest 10.

Filtering is the clean fix for genuinely ambiguous questions. “What is my rate limit?” has three different correct answers in this corpus depending on plan — no reranker can resolve that, because the missing information is not in the question. The filter supplies it.

Pre-filter vs post-filter. Exact search filters for free: shrink, then rank. A graph index cannot — which is why Qdrant needs payload indexes to filter without wrecking recall.
03

Cross-encoder rerank rerank.py → rerank()

The bi-encoder never saw the query and the chunk together — it compared two vectors made independently. The cross-encoder feeds [query, chunk] through the transformer as one input, so it can model word-level interaction. It costs a full forward pass per pair, which is why it only ever sees 10.

Raw output is an unbounded logit, roughly −11 to +11. A sigmoid puts it on a 0–1 probability scale so the gate threshold means something. Sigmoid is monotonic, so this never reorders — it only makes the number interpretable.

04

Score gate pipeline.py

The decision point. Detailed in section 04.

05

Generate, then verify generate.py

The prompt supplies only the surviving excerpts, each labelled with the exact ticket id the model is asked to cite. Afterwards every citation the model emitted is checked against what it was actually shown.

04 — THE GATE

Four ways out

This is the part that makes the app trustworthy rather than merely fluent. Three of the four exits produce “I don't know”, and two of those never spend a token.

no-candidates

The metadata filter removed everything. There is nothing to reason over.

LLM not called
below-threshold

Best cross-encoder score fell under 0.20. The corpus does not contain the answer, so refuse rather than let the model improvise from weak context.

LLM not called
model-refused

Context passed the gate but the model still declined. Its sources are stripped — attaching citations to a non-answer credits documents for something they never said.

LLM called · sources cleared
answered

Citations parsed and checked against the supplied excerpts. Any id the model invented is reported as a hallucinated citation.

LLM called · citations verified
# in the corpus > .\rag.cmd ask "How long does a bank transfer refund take?" --quiet Answer: Bank transfer refunds take 15 business days from approval [TIC-1005]. Sources: TIC-1005 (K=10 → N=3; best_score=0.9998; threshold=0.2; used_llm=True; gate=answered) # not in the corpus > .\rag.cmd ask "What are your phone support opening hours?" --quiet Answer: I don't know — that information is not in the provided documents. Sources: (none) (K=10 → N=3; best_score=0.0005; threshold=0.2; used_llm=False; gate=below-threshold)

used_llm=False is the observable proof. Not that the model declined — that it was never asked.

05 — THE DEFECT

Why chunking strategy beats chunk size

Support tickets have hard boundaries. A character window does not know that, so it produces chunks that begin inside one ticket and end inside the next — and the chunk is then cited as whichever ticket it started in.

Preset A · flat / 500 chars — the window ignores the seam
TIC-1001

Free plan is capped at 60 requests per minute per API key. Once you cross it we return 429 with a Retry-After header telling you how many seconds to wait. Check X-RateLimit-Remaining on every response.

TIC-1002

Pro is 600 requests per minute per API key. Your batch job is bursting to roughly 900 req/min for short windows. The limiter uses a fixed one-minute window, not a rolling average.

500-char window → cited as [TIC-1001]
✕ The chunk contains Pro's 600 req/min but is attributed to TIC-1001, the Free-plan ticket. A confident answer with the wrong source.
Preset C · ticket / one chunk each — the window is the boundary
TIC-1001

TIC-1002

Pro is 600 requests per minute per API key. Your batch job is bursting to roughly 900 req/min for short windows. The limiter uses a fixed one-minute window, not a rolling average.

✓ Every citation names exactly the ticket its text came from. Structure supplies the boundary, so it cannot be crossed.

Doubling the chunk size made bleeding worse, not better — 70% → 97%. Larger windows span more boundaries. The instinct that bigger chunks preserve more context is right for continuous prose and exactly wrong for a corpus of discrete records. Preset C uses the largest chunks of all and bleeds nothing, because its boundaries are the document's own.

Preset A is kept deliberately as the negative control. It is not a bug to fix.

06 — GROUNDING

Four checkpoints, not one

“Only answer from the documents” is a prompt instruction, and prompt instructions are suggestions. These four are enforcement.

01

Score gate — refuse before generating

Reads the rerank score, not the retrieval score. Cosine similarity is always positive-ish and would not gate anything useful.

02

Prompt labels match the citation format

Excerpts are labelled [TIC-1001] — the exact token the model is asked to cite. Labelling them [1], [2] while demanding ticket ids teaches the wrong format by example, and the model will emit what it can see.

03

Refusal detection strips sources

Matching is punctuation-normalized. Models routinely rewrite the em dash in the canonical refusal string, and an exact comparison would classify a correct refusal as a real answer and then attach citations to it.

04

Citation verification

Every id the model emitted is checked against what it was shown. A citation naming a ticket that was never in the context window is the clearest possible grounding failure — and completely invisible unless you look for it.

07 — EVIDENCE

Does it actually work?

20 questions with known answers, plus 4 deliberately absent from the corpus so the refusal path is measured rather than assumed. Runs without the LLM, so it is free.

hit@K is the ceiling — if the right ticket never enters the top 10, no reranker can recover it. False refusals counts only cases where the right ticket was at rank 1 and the gate threw it away anyway; refusing when the top hit is wrong is the gate doing its job, and is counted separately.

The threshold itself was picked by sweeping it, not by feel — eval --sweep replays the gate across values and shows where false refusals start. It is tuned on 36 synthetic tickets and will not transfer to a real corpus.

Week 2

Debugging Retrieval

Same app. The app from week 1 works, but sometimes it's wrong — and "wrong sometimes" isn't fixable. This chapter separates the two kinds of wrong, tries exactly one fix, and reports the number honestly, including what it didn't fix.

08 — FAILURE SEPARATION

Wrong document, or right document, wrong answer

These are different bugs with different fixes. A smarter model fixes neither reliably — it can't invent a document retrieval never handed it, and it can just as easily still misread one that was right there. label_failures() in evaluate.py sorts every gold question into a bucket by running the real pipeline, not a re-derivation of its logic — so a label reflects exactly what the live app did.

09 — THE ONE CHANGE

Add BM25, fuse by rank position (RRF)

Dense retrieval compares meaning — it can match "why do I keep getting cut off" to "rate limit exceeded" with no shared words. It is correspondingly bad at the opposite case: an exact token is just one point in embedding space among many. BM25 is the other direction — deterministic exact-term overlap, implemented from scratch in bm25.py rather than via a dependency, the same reason the numpy store is hand-rolled.

Reciprocal Rank Fusion combines two rankings by position, not score — a cosine similarity and a BM25 score live on incomparable scales, so summing them directly is an arbitrary weighting in disguise. RRF(d) = Σ 1/(k+rankr(d)) across every ranking that contains d. This is the one thing this section changes: chunking, embedding, the cross-encoder and the score gate are all untouched, so a before/after comparison isolates exactly this fusion's effect.

TIC-1005 (A), TIC-1027 and TIC-1007 (B) — missed under dense, still missed under hybrid. This change did not touch them.

Verdict: hybrid search did not help this corpus. It cost nothing on the already-clean presets C and D (retrieval was already at 95–100% hit-rate@3 — a ceiling effect, no failures left to fix), and it mildly hurt the flat-chunked presets A and B. The root cause is upstream: last week's chunking-bleed defect means flat's chunks contain boilerplate and neighbour-ticket text, and BM25 latches onto that shared vocabulary just as readily as it would latch onto a genuinely relevant term. Hybrid search is not a fix for bad chunking — it can amplify the confusion just as easily as resolve it.

retrieval.mode stays at dense in config.yaml because that is what the numbers say to do. The code path is real and tested either way — worth revisiting on a larger or more keyword-heavy corpus, not this one.

11 — RUNNING IT

Commands

Drop .jsonl files into data/tickets/, then ingest. There is no file watcher and no UI — every step is explicit.

# inspect chunking — instant, loads no models > .\rag.cmd chunks --all --show 2 # build the stores (required before asking) > .\rag.cmd ingest --all # ask, with and without a metadata filter > .\rag.cmd ask "How many MFA backup codes are issued?" --quiet > .\rag.cmd ask "what is my rate limit?" --filter customer_tier=pro # interactive session — models load once, then ask freely > .\rag.cmd chat # same question across all four presets, with a summary table > .\rag.cmd compare "what is my rate limit?" # score retrieval and the refusal gate; --sweep tunes the threshold > .\rag.cmd eval --all --sweep # the ONE-change before/after: dense vs dense+BM25 hybrid, hit-rate@3 > .\rag.cmd eval --all --compare-retrieval # label each gold question: wrong document, vs right document/wrong answer > .\rag.cmd debug --preset B --generate # embedding model registry and per-family prefix rules > .\rag.cmd models
