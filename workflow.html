01 — INGEST

Step 1 of 4 — getting documents into the app

01

Load documentstickets.py → load_all()

Q: what format do documents have to be in before anything else can happen?

Options considered

Generic file loader

Accept whatever shows up — PDF, DOCX, plain markdown — and extract raw text from each.

+ Drop in anything, no schema to satisfy.

− Throws away structure: no ticket id, product, status, or plan to filter or cite by.

Database connector

Read tickets live from wherever the real help desk stores them (Zendesk, a SQL table).

+ Always current, no export step.

− A live dependency and credentials just to study retrieval — the wrong trade for this project.

Chosen Structured JSONL, one ticket per line

A fixed schema: ticket_id, subject, product, category, status, priority required; conversation and resolution carried as real fields, not flattened into one blob of text.

+ Metadata rides along to every chunk, for filtering and exact citations.

− A different real corpus needs a new loader — this one only reads this shape.

Why, for this project

This app was actually built the generic way first — data/docs/*.md and the unused docs_dir config field are what's left of that attempt, kept as a fossil rather than deleted. It got replaced because a flat markdown file has no product, no status, no ticket id to cite — exactly the metadata that later makes filtering (step 6) and trustworthy citations (step 9) possible at all. A malformed JSONL line raises immediately, naming its own file and line number, rather than silently skipping a bad ticket.

ticket_id is the one field with an extra job: it becomes the literal citation label — it's what shows up as [TIC-1001] in the final answer.

02

Chunkchunking.py → build_chunks()

Q: how do we split ticket text into pieces small enough to embed and cite accurately?

Options considered

Flat character windows

Concatenate every ticket into one document, then slice it every N characters, ignoring where one ticket ends and the next begins.

+ Trivial to implement, works on any text, no document structure needed.

− A window can start in one ticket and end in the next — see the measurement below.

Chosen (default) One chunk per ticket

Each ticket becomes exactly one chunk (splitting further only if a single ticket exceeds the size limit).

+ The boundary IS the document — a citation can never span two tickets.

− A very long ticket still needs a fallback split.

Turn-based / section

Pack conversation turns together under a repeated header naming the ticket, so even a partial fragment is self-describing.

+ Resilient to long tickets without losing the "no bleed" guarantee.

− More chunks total; the header text repeats, costing a little storage.

Semantic / recursive splitting (exists elsewhere, not built here)

Split on embedding-distance jumps between sentences, or recursively by markdown/HTML structure (the common LangChain-style approach).

+ Adapts to prose that has no other structure.

− Unnecessary here — tickets already have a hard structural boundary (the ticket itself); using it is simpler and stronger than inferring one.

Why, for this project

All four strategies exist in the codebase as configurable presets (A/B = flat at two sizes, C = ticket, D = section) specifically so the effect is measurable, not assumed. It is:

03

Embed documentsembed.py → encode_documents()

Q: how do we turn each chunk's text into something searchable by meaning?

Options considered

Keyword index only (BM25)

Score chunks by exact term overlap with the query — no vectors at all.

+ Perfect for exact codes and ids, zero model cost.

− Matches words, not meaning — "cut off" never finds "rate limit exceeded".

Chosen Bi-encoder embeddings

A transformer turns each chunk into a fixed-length vector, once, at ingest time — query and document vectors are compared later with plain cosine similarity.

+ Pre-computed per document; a search is one matrix multiply.

− Never sees the query and the document together — can't model fine word-level interaction (that's what step 7, rerank, is for).

Hosted embedding API (OpenAI, Cohere)

Send text to a paid API and get a vector back, instead of running a model locally.

+ No local GPU/CPU cost, often strong quality.

− Network dependency and per-token cost for something that runs constantly at ingest.

Which bi-encoder — also a real, swappable choice

Why, for this project

MiniLM is the default because it's symmetric (no prefix bookkeeping to get wrong), small enough to run on CPU in this demo, and close enough on MTEB's retrieval column to the larger alternatives that the difference doesn't matter at 36 tickets. BGE and E5 are wired in and swappable via bi_encoder_model in config.yaml — the point of keeping three is that E5 and BGE are asymmetric: the query needs a different prefix than the document. Get that backwards and retrieval quietly gets worse with no error at all — which is exactly why encode_queries() and encode_documents() are two different methods instead of one, so the prefix can never be forgotten on one side.

04

Persiststore.py / qdrant_store.py

Q: where do the vectors live so a question can search them later?

Options considered

Chosen (default) Hand-rolled numpy store

Vectors in one array, search is a matrix multiply plus a top-k sort — brute force, exact, no approximation.

+ Zero dependencies, fully inspectable, always exactly correct.

− O(N) per query — fine at 36 tickets, not at 36 million.

Also implemented Qdrant

A real vector database behind the same interface — embedded (a local file, prototyping) or a server (real HNSW).

+ Real payload filtering, real persistence API, a real HNSW index — if you run the server.

− Embedded mode is brute force too — it accepts HNSW config and quietly ignores it.

Chroma / pgvector / Pinecone (not implemented)

Other real vector stores with the same job: Chroma (easiest embedded start), pgvector (it's just Postgres — joins and one backup story), Pinecone (managed, no ops).

+ Each fits a different production constraint.

− Out of scope here — the goal was proving the numpy-vs-real-vector-DB interface generalizes, not surveying every vendor.

Why, for this project

At 36 tickets, exact brute force is both correct and fast — there's no accuracy to trade away for speed yet, so reaching for an approximate index would add complexity with no benefit. numpy stays the default specifically because it's inspectable: you can open vectors.npy and see exactly what's stored. Qdrant exists alongside it, behind the identical SearchBackend interface, so the vector-DB concepts (payload filtering, HNSW's recall/latency trade) are real and testable rather than just described. A meta.json written next to every store records which embedding model built it — swap models without re-ingesting and you'd otherwise get a raw shape error, or worse, silently wrong rankings when dimensions happen to match.

05

Embed the questionembed.py → encode_queries()

Q: does the question get embedded the same way as a document?

Same model as ingest, but the query side of the asymmetry (step 3). No new decision here — this exists as its own step because forgetting the distinction is the single easiest way to quietly break retrieval on an asymmetric model.

06

Retrieveretrieve.py / filters.py / hybrid.py

Q: out of every chunk in the store, which ones are even worth reranking?

Options considered — candidate generation

Chosen (default) Dense only (cosine)

Rank every chunk by cosine similarity to the query vector, take the top 10.

+ Catches paraphrase with zero shared vocabulary.

− Weak on exact tokens (ids, codes) — just one point in embedding space among many.

BM25 only

Rank by exact keyword overlap instead — see step 12 (Week 4).

+ Deterministic on exact terms.

− Blind to meaning entirely.

Hybrid (dense + BM25, fused by RRF)

Built and measured in Week 4 — retrieval.mode: hybrid in config.

+ In principle, the best of both.

− Measured on this corpus: didn't help. Full story in section 13.

A second, independent lever — metadata filtering

Available, opt-in --filter product=Billing

Shrink the candidate set to matching metadata before ranking, using fields that rode along since step 1 (product, status, plan tier).

+ Solves genuine ambiguity a reranker structurally cannot — "what's my rate limit?" has three different correct answers in this corpus depending on plan, and the missing information isn't in the question at all.

− Requires the caller to know and supply the right field.

Why, for this project

Dense retrieval is the default because this corpus is mostly natural-language paraphrase questions, which is exactly what a bi-encoder is good at. Filtering and hybrid search solve different problems and both stayed in the codebase rather than picking one: filtering resolves ambiguity that's structurally unresolvable by ranking alone (see section 06), while hybrid search was a genuine experiment (section 13) whose answer turned out to be "no" for this corpus.

Pre-filter vs. post-filter matters here: exact search filters for free — shrink the candidate set, then rank. An approximate graph index (HNSW) cannot do this cleanly, which is why Qdrant needs a payload index up front to filter without wrecking recall.

07

Rerankrerank.py → rerank()

Q: is the bi-encoder's top-10 ordering good enough to hand to the LLM as-is?

Options considered

No reranking

Trust the bi-encoder's cosine order and hand the top 3 straight to generation.

+ One fewer model, one fewer forward pass.

− Cosine alone can't tell "Free plan, 60/min" from "Pro plan, 600/min" apart cleanly — near-duplicates confuse it.

Chosen Cross-encoder reranking

Feed [query, chunk] through the transformer together, one pair at a time, and re-sort by that score.

+ Reads word-level interaction the bi-encoder structurally cannot.

− A full forward pass per candidate — only affordable because it only ever sees 10, not the whole corpus.

Hosted reranker (Cohere Rerank, BGE-reranker API)

Same idea as the cross-encoder, run as a paid API instead of a local model.

+ Often stronger, no local model to manage.

− Network + cost per query, for a project meant to run fully offline.

MMR (different job, not a substitute)

Maximal Marginal Relevance re-sorts for diversity — penalizing near-duplicate results — not for relevance.

+ Useful when top-10 is five copies of the same fact.

− Doesn't address "is this chunk actually relevant" at all — a complement to reranking, not a replacement.

Why, for this project

The bi-encoder never saw the query and the chunk together — it compared two vectors made independently, at different times. The cross-encoder is the one stage built specifically to fix that blind spot, and it's the most CPU-expensive stage per item for exactly the same reason: reading both texts together is what makes it accurate, and what makes it too slow to run over the whole corpus. Raw output is an unbounded logit (roughly −11 to +11); a sigmoid squashes it onto 0–1 so the next step's threshold means something interpretable. Sigmoid is monotonic, so this never changes the ranking — only the number.

08

Score gatepipeline.py

Q: is the best reranked chunk actually good enough to answer from?

Options considered

No gate

Always pass the top chunks to the LLM, regardless of how weak the match is.

+ Never refuses.

− The LLM will confidently answer from irrelevant context — the classic RAG hallucination.

Fixed, guessed threshold

Pick a cutoff that "feels right" and hard-code it.

+ Simple.

− No evidence it's actually the right number for this reranker, this corpus, this scale.

Chosen Calibrated threshold, tuned by sweeping real data

eval --sweep replays the gate across many thresholds against the gold set and reports where false refusals start.

+ The number (0.20) is evidence, not a guess.

− Tuned on this corpus — will not transfer to a different one without re-sweeping.

Why the gate reads the RERANK score, not retrieval

Cosine similarity from step 6 is always positive-ish and would not gate anything useful — it has no calibrated zero point. The sigmoid-scaled cross-encoder score does. Below 0.20, refuse and never call the LLM — used_llm=False is the observable, testable proof that this happened, not just a claim in a log line.

09

Generate, then verifygenerate.py

Q: once the gate says "yes", how do we stop the LLM from wandering off the excerpts?

Options considered

Unconstrained prompting

Paste the context, ask the question, take whatever comes back.

+ Simplest possible prompt.

− No citations to check, no format to hold the model to.

Prompt-only constraints

Instruct the model to cite sources and refuse when unsure — and trust that it does.

+ Better than nothing.

− A prompt instruction is a suggestion — models drift, especially under pressure to be helpful.

Chosen Constrained prompt + programmatic verification

Require exact-id citations matching the excerpt labels, then check every emitted citation against what was actually shown.

+ Catches drift instead of trusting it away.

− More moving parts — four separate checks, all of which must survive a refactor.

The four checks that make "constrained" actually true

01

Score gate — already covered in step 08

Refuses before generation ever starts, on the rerank score specifically.

02

Prompt labels match the citation format

Excerpts are labelled [TIC-1001] — the exact token the model is asked to cite. Labelling them [1], [2] while demanding ticket ids teaches the wrong format by example.

03

Refusal detection strips sources

Matching is punctuation-normalized — models rewrite the em dash in the refusal string constantly, and an exact string comparison would misclassify a correct refusal as a real, sourced answer.

04

Citation verification

Every id the model emitted is checked against what it was actually shown. A citation naming a ticket never in context is reported as hallucinated — invisible unless you look for it on purpose.

Week 4

Debugging Retrieval

Same app. The app from week 3 works, but sometimes it's wrong — and "wrong sometimes" isn't fixable on its own. This chapter separates the two kinds of wrong, tries exactly one fix, and reports the number honestly, including what it didn't fix.

10 — DIAGNOSIS

Step 1 — before fixing anything, name which bug it is

10

Failure separationevaluate.py → label_failures()

Q: when the app answers wrong, is that a retrieval bug or a generation bug?

Options considered

Treat every wrong answer the same

Log "wrong" and move on to the next question.

+ No extra machinery.

− A smarter model fixes only ONE of the two bug types — you can't tell which fix to reach for.

Chosen Sort every failure into a named bucket, by running the real pipeline

label_failures() reuses ask() itself — not a re-derivation of its logic — so a label reflects exactly what the live app did, including the gate.

+ Points the next fix at the right stage.

− Confirming a "generation" bucket needs a real LLM call — free retrieval-only checks can only prove "retrieval" or leave a case "unconfirmed".

The two buckets

retrieval — the ticket never reached the final top-3 shown to the LLM. No model, however good, could have answered correctly; the boundary is membership in the reranked list, not "rank exactly 1".

generation — the ticket was in context, and the app still produced a wrong answer — via the score gate refusing on a passing document, or the model itself missing what it was handed.

Five real cases from .\rag.cmd debug --preset B --generate — one run against the live pipeline, no cherry-picking:

"duplicate charge" — expects TIC-1007

Never entered the retrieved candidate set at all — the bi-encoder's fault. Two questions, two different pipeline stages at fault; "retrieval failure" is not one bug.

generation

Two of these five never had a chance — the document was never in front of the model. The other three prove the opposite failure exists too: the document was right there, and the app said "I don't know" anyway, for two different reasons (gate threshold, model judgment). Conflating these into one "it's wrong" bucket would point the next fix in the wrong direction for 3 of these 5 questions.

11 — THE ONE CHANGE

Step 2 — try exactly one retrieval fix, measure it

11

Improve retrievalbm25.py / hybrid.py

Q: which one retrieval-side change is worth trying first?

Options considered — the mentor rule is ONE change, not five

Query rewriting

Ask an LLM to rewrite a messy question into a cleaner search query before embedding it.

+ Can fix genuinely garbled input.

− Costs an extra LLM call per question, and can rewrite AWAY the exact wording that would have matched.

HyDE

Generate a hypothetical answer first, then embed that and search with it instead of the raw question.

+ Can bridge a big vocabulary gap between question and answer style.

− Another LLM call per question; the hypothetical answer can be confidently wrong and mislead the search.

Chosen — this is the ONE change tested Hybrid: dense + BM25, fused by RRF

Add a from-scratch keyword index (bm25.py) and combine it with the existing dense ranking by Reciprocal Rank Fusion — position only, never blending raw scores from two incomparable scales.

+ No extra LLM call; catches exact ticket ids and codes dense retrieval structurally can't prioritize.

− Result below: measured, didn't help on this corpus.

MMR / better reranker

Diversify the candidate set (MMR), or pay for a stronger reranker (Cohere Rerank, BGE-reranker).

+ Each addresses a real, different weakness.

− Testing more than one change at once means you can't tell which one moved the number.

Reciprocal Rank Fusion combines two rankings by position, not score — RRF(d) = Σ 1/(k+rankr(d)) across every ranking containing d. A cosine similarity and a BM25 score live on incomparable scales, so summing them directly would just be an arbitrary, hidden weighting. This is the one thing this section changes: chunking, embedding, the cross-encoder, and the score gate are all untouched, so the before/after comparison below isolates exactly this fusion's effect.

Verdict, stated plainly

Hybrid search did not help this corpus. Nothing on the already-clean presets C and D (retrieval was already at 95–100% hit-rate@3 — a ceiling effect, no failures left to fix), and a mild regression on the flat-chunked presets. The root cause is upstream, not in the fusion math: flat chunking's boundary-bleed defect (step 02) means those chunks contain boilerplate and neighbour-ticket text, and BM25 latches onto that shared vocabulary just as readily as it would latch onto a genuinely relevant term. Hybrid search is not a fix for bad chunking — it can amplify the confusion as easily as resolve it. retrieval.mode stays at dense in config.yaml because that's what the numbers say, not a guess.

Week 5

Error Analysis

Eval and debug (weeks 3–4) measure known behaviors — the gold set is curated on purpose, to confirm things already suspected. This chapter does the opposite: read a fair, uncurated sample of real answers, and find the problems nobody predicted.

12 — SAMPLING

Step 1 — get a fair sample to read, not a convenient one

12

Choose what to readsampling.py → sample_questions()

Q: which ~20 answers do you actually sit down and read?

Options considered

Read the curated gold set again

Reuse evaluate.GOLD — the 26 questions already built to test known behaviors.

+ Already exists, already has known-correct answers to check against.

− You already designed these to probe things you suspected — reading them is reading "the good examples", not a fair sample.

Hand-pick 20 interesting-looking questions

Skim recent usage and choose ones that look worth a closer look.

+ Feels efficient.

− "Interesting-looking" is a bias — you find the failures you already know how to spot.

Chosen A second, uncurated pool + a seeded random draw

57 questions with no answer key — clean lookups, ambiguous/compound/casual phrasing, out-of-corpus topics, false premises, fabricated ticket ids. sample_questions(n, seed) draws reproducibly.

+ The seed makes the sample provably not hand-picked after the fact — anyone can rerun it and get the same 20 back.

− No population of real end users behind this app, so this is the most honest available substitute, not the real thing.

A test enforces zero overlap between this pool and GOLD — sampling from your own curated test set would be grading your own exam. Every trace is written to disk as a complete, replayable record (question, every retrieved/reranked chunk with its score and a text preview, the gate outcome, the final answer) specifically because Answer otherwise vanishes the moment the process exits — there'd be nothing left to read cold, a week later.

Not the highest raw frequency, but the severity ceiling is what matters: this is the only finding where the failure mode, if it ever actually fires, is a confidently wrong answer attributing real content to a ticket that doesn't exist. In the sample it was caught twice by two different, uncoordinated mechanisms — the model's own judgment once, an absence of lucky keyword overlap once — neither of which is a deliberate check.

Prediction, written before implementing anything

If the pipeline extracts any TIC-####-shaped token from the question and checks it against the retrieved chunk sources before generation: (1) those two traces get a specific refusal instead of the generic one, (2) the dependency on model judgment for this failure mode drops to zero, (3) no regression on the 26-question gold set, since none of them reference a ticket id at all. Re-running the same sample after the fix is how this gets checked against reality, not just declared successful.

Benchmarks vs. this eval. MMLU and HumanEval measure a model's general capability, the same way regardless of what you build with it. GOLD and this taxonomy measure something a public benchmark structurally cannot: does this app, over this corpus, with these chunking/retrieval/gate settings, answer correctly and refuse when it should. A model that tops MMLU can still fail every question here if the chunking bleeds or the threshold is miscalibrated.
14 — RUNNING IT

Commands

Drop .jsonl files into data/tickets/, then ingest. There is no file watcher and no UI — every step above is a command you type on purpose.

# inspect chunking — instant, loads no models > .\rag.cmd chunks --all --show 2 # build the stores (required before asking) > .\rag.cmd ingest --all # ask, with and without a metadata filter > .\rag.cmd ask "How many MFA backup codes are issued?" --quiet > .\rag.cmd ask "what is my rate limit?" --filter customer_tier=pro # interactive session — models load once, then ask freely > .\rag.cmd chat # same question across all four presets, with a summary table > .\rag.cmd compare "what is my rate limit?" # score retrieval and the refusal gate; --sweep tunes the threshold > .\rag.cmd eval --all --sweep # the ONE-change before/after: dense vs dense+BM25 hybrid, hit-rate@3 > .\rag.cmd eval --all --compare-retrieval # label each gold question: wrong document, vs right document/wrong answer > .\rag.cmd debug --preset B --generate # draw a fair random sample of real traces for error analysis > .\rag.cmd sample --n 20 --seed 42 --generate # embedding model registry and per-family prefix rules > .\rag.cmd models
Where each stage lives
ModuleResponsibility
tickets.pyLoad the .jsonl drop, render ticket text, carry metadata
chunking.pyThree strategies; records bleed per chunk
embed.pyBi-encoder + per-family query/passage prefixes
store.pynumpy brute force, filtering, provenance
qdrant_store.pyQdrant backend, payload indexes, HNSW caveats
retrieve.pyTop-K, the seam where backends swap
bm25.pyKeyword search, from scratch — no dependency
hybrid.pyRRF fusion of dense + BM25 rankings
rerank.pyCross-encoder + sigmoid scaling
generate.pyPrompt, refusal detection, citation verification
pipeline.pyThe only orchestrator. Holds the gate.
evaluate.pyGold set, hit@K/MRR, threshold sweep, failure labeling, retrieval-mode comparison
sampling.pyUncurated question pool + seeded random sampler
traces.pyDurable, replayable records of real answers
repl.pyThe chat session — caches store, models and BM25 index per preset

Every other module is a single stage that knows nothing about its neighbours. If you read one file to understand the system, read pipeline.py.
